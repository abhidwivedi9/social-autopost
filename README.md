# Social Autopost — Daily X + LinkedIn automation

Fully automatic, 5 posts/day, different content angle per slot, generated by the Claude API,
running as Kubernetes CronJobs on your existing GKE Autopilot cluster.

## Slots

| Time (IST) | Topic | Auto-publishes? |
|---|---|---|
| 6:00 AM | AI & latest tech | Yes |
| 9:00 AM | Tech career content | Yes |
| 1:00 PM | Startup idea (family safety suite) | Yes |
| 5:00 PM | Gaming & gadgets | Yes |
| 9:00 PM | Gaming industry policy | **No — logs for review** |

The 9 PM slot is scoped to gaming-industry policy topics (loot boxes, esports governance, age
ratings) rather than general politics, and does NOT auto-publish — it generates the post and
logs it so you can review before it goes out. You can wire a Slack/Telegram webhook into
`src/index.js` (search for `requiresReview`) to get pinged instead of checking logs.

## One-time setup

### 1. Anthropic API key
You already have this if you've used the Claude API before. Get one at console.anthropic.com if not.

### 2. X (Twitter) API access
1. Go to developer.x.com → create a project + app.
2. Set app permissions to **Read and Write**.
3. Generate: API Key, API Secret, Access Token, Access Token Secret.
4. Free tier posting limits apply — check current limits on the X dev portal before relying on 5 posts/day per account.

### 3. LinkedIn API access
1. Go to developer.linkedin.com → create an app.
2. Request the **"Share on LinkedIn"** product (self-serve, usually approved quickly — this is
   different from the heavier Marketing/Partner APIs).
3. Complete OAuth 2.0 flow once to get a long-lived access token with `w_member_social` scope.
4. Get your Person URN by calling `GET https://api.linkedin.com/v2/me` with your token —
   the response `id` field goes into `urn:li:person:{id}`.
5. LinkedIn access tokens expire (~60 days) — you'll need to refresh periodically. If this
   becomes a hassle, Buffer's API is a reasonable fallback for the LinkedIn leg only.

### 4. Build and push the image
Reuse your existing GitLab CI → GKE Autopilot pipeline pattern:
```bash
docker build -t asia-south1-docker.pkg.dev/terraform-gke-learning/social-autopost/poster:latest .
docker push asia-south1-docker.pkg.dev/terraform-gke-learning/social-autopost/poster:latest
```

### 5. Deploy secrets and CronJobs
```bash
cp k8s/secret.example.yaml k8s/secret.yaml
# fill in real values in k8s/secret.yaml
kubectl apply -f k8s/secret.yaml

# edit k8s/cronjobs.yaml: replace IMAGE_PLACEHOLDER with your pushed image
kubectl apply -f k8s/cronjobs.yaml
```

### 6. Test locally before trusting the schedule
```bash
npm install
cp .env.example .env   # fill in real values
npm run test:6am       # try each slot manually first
```

## Cloud Run deployment (free, always-on, works even if your laptop is off)

This uses **webhook mode** instead of polling, so Cloud Run can scale to zero and
stay within the free tier at personal-post-volume usage.

### 1. Build and push the image
```bash
gcloud builds submit --tag asia-south1-docker.pkg.dev/terraform-gke-learning/social-autopost/bot:latest
```
(Or reuse your existing docker build/push flow if you prefer.)

### 2. Deploy to Cloud Run
```bash
gcloud run deploy social-autopost-bot \
  --image asia-south1-docker.pkg.dev/terraform-gke-learning/social-autopost/bot:latest \
  --region asia-south1 \
  --allow-unauthenticated \
  --min-instances=0 \
  --set-env-vars ANTHROPIC_API_KEY=xxx,X_API_KEY=xxx,X_API_SECRET=xxx,X_ACCESS_TOKEN=xxx,X_ACCESS_SECRET=xxx,TELEGRAM_BOT_TOKEN=xxx,TELEGRAM_CHAT_ID=xxx,SCHEDULER_SECRET=pick-a-random-string
```
(Better: use `--set-secrets` with Secret Manager instead of plaintext env vars —
worth doing once this is working, since these are the same credentials you've
already had to rotate a few times.)

### 3. Set PUBLIC_URL and redeploy (registers the Telegram webhook)
```bash
SERVICE_URL=$(gcloud run services describe social-autopost-bot --region asia-south1 --format 'value(status.url)')
gcloud run services update social-autopost-bot --region asia-south1 --set-env-vars PUBLIC_URL=$SERVICE_URL
```

### 4. Create the Cloud Scheduler jobs
Edit `k8s/setup-cloud-scheduler.sh` — fill in `SERVICE_URL` and `SCHEDULER_SECRET`
(the same secret you set in step 2), then:
```bash
bash k8s/setup-cloud-scheduler.sh
```

### Note on state
The bot keeps "pending post" state (waiting for your ✅/🔄/❌ tap) in memory.
Since this is a single-user personal tool and Cloud Run keeps an instance warm
for a while after each request, this works fine in practice — but if you leave
a preview unanswered for a long time and the instance scales down, you might
occasionally see "Expired, pick a topic again." Just re-trigger with `post` if
that happens.

## Notes
- Topics rotate day-to-day within each category (5 sub-topics per slot) so content doesn't repeat weekly.
- X's 280-char limit is enforced with a safe trim; LinkedIn has no practical limit for short posts.
- Check `kubectl logs job/<job-name>` after each run while you're validating it.
- Once you're confident in the 9 PM slot's output quality, you can remove the `requiresReview`
  flag in `src/config.js` to make it fully hands-off too.
